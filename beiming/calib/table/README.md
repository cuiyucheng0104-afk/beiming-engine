# 探针数据表（Mac 和 5090 两台机器的读数，没定稿）

两个一次性探针适配器各把六个校准场景渲了两遍，逐条读数在同目录的 `three.json` 和 `blender.json`。这张表是按行的汇总：两个帧源各量到什么、差多少、契约照它该怎么写。

**两台机器都量过了。**Mac：three 是 0.187.0 的 WebGL 渲染器，Blender 是 5.2.0 的 Cycles（CPU，64 采样，不降噪），读数在 `three.json`、`blender.json`。5090（Linux）：同一个 three 版本走 ANGLE Vulkan，Blender 是 5.2.3 的 Cycles（显卡，OptiX，64 采样，不降噪），读数在 `three.linux-5090.json`、`blender.linux-5090.json`。下表各行写的是 Mac 的读数；5090 上哪些一样、哪些不一样，见表后面的「5090 读数」一节。契约里的 `待探针` 还没回填。

「能不能回填」一栏：**口径**指这一行已经能定契约里「用哪种算法、哪个定义」；**数值**指能不能把过线的数填进契约。

## 5090 读数（2026-11-19）

机器：Linux，RTX 5090。three 用系统装的 Chrome 157，`--use-angle=vulkan`；Blender 5.2.3 LTS，Cycles，64 采样，不降噪，种子 0。机器是共用的，跑的时候显卡占用 7%，耗时读数会受别人的任务影响。这一遍是在远端的临时目录里直接跑的，没有走 `tools/remote` 的按提交运行，所以没有 `out/remote/` 下的运行记录。

| 项 | 读数 | 对契约意味着什么 |
|---|---|---|
| 口径类各行（线性度、深度、编号边缘、坐标与相机、时间键、快门相位、可见比例） | 和 Mac 的读数一致：同名读数里没有超过千分之一的差（耗时类除外） | 这几行定的口径不随机器变 |
| three 的确定性 | 六个场景两遍，颜色层哈希 6/6 相同；而且和 Mac 上的哈希 6/6 相同 | three 帧源的颜色层可以要求逐位相同；这六个场景上跨机器、跨显卡后端也相同 |
| Blender 的确定性：显卡（OptiX） | 21 个文件两遍：7 个逐位相同，14 个不同。不同的只有颜色层，共约 2,190 个数，最大绝对差 3e-5，最大相对差 1.7e-6；深度、编号、位置三层全部逐位相同。连跑三次，量级不变 | 显卡上的 Blender 颜色层做不到逐位相同，只能要求「在容差内」；辅助层可以要求逐位相同 |
| Blender 的确定性：显卡（CUDA） | 同样不逐位相同：约 2,190 个数，最大相对差 1.7e-6 | 换显卡后端解决不了 |
| Blender 的确定性：CPU（同一台机器、同一个 5.2.3） | 21 个文件两遍全部逐位相同 | 要逐位相同的地方（比如立基线、做回归）只能用 CPU 渲 |
| 耗时：three | 起浏览器到渲染器建好 356 到 412 毫秒；单帧中位 0.3 毫秒；整张浮点颜色层读回中位 2.4 毫秒 | 和 Mac 同量级 |
| 耗时：Blender 显卡 | 单帧（含写 EXR）277 到 343 毫秒；四分之一分辨率、1 采样的编号层单独多渲一遍 279 到 305 毫秒（Mac 的 CPU 是 2 毫秒） | 显卡每渲一次有约 0.3 秒的固定开销，和画面多小无关。给每个实体单独多渲一遍编号层这种小活，用显卡比用 CPU 慢两个量级 |

没量的：这六个场景都很小，说明不了真实场景的渲染速度；显卡上的差随采样数、场景复杂度怎么变没量；降噪打开之后的确定性没量。

## 读这张表要知道的

- 两列读数各过了一次独立复核，复核都重跑过适配器。three 一列第一次没过（快门相位那一行当时不是测量；判旋转顺序的读数没有从渲染结果读回），修了一轮后通过。
- three 一列里「three 投影像素」这类读数是矩阵算出来的，没经过光栅化，只证明 three 的矩阵数学和检查器一致；从渲染读回的读数在名字里写了「渲染」。
- Blender 一列里「渲染·编号层重心偏移」这类读数比的是两张编号图，逐像素相同时差就是 0，只到像素级；亚像素的差看「编号层重心直接对期望值」那几条。
- 校准场景本身有一处要小心：转台场景的标记块在第 24 帧被 X 轴的杆挡住下半截，合渲时它的质心会偏 2.3 像素；量它要单独渲。
- 两个适配器在 `../adapters/`，是一次性的，这张表定稿后删掉。
