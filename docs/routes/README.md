# 双路线工程手册

这里把 [ROUTES.md](../../ROUTES.md) 的路线选择展开到实际文件、参数、接口、任务和验收。先区分三种状态：

| 状态 | 内容 |
|---|---|
| 已运行 | 原 Three 样片；独立 RAEA 10 秒实验；GLB 转换与回读；历史 5090 和目录迁移后的 Mac 验证 |
| 本次可执行工具 | `routes:check` / `routes:next`：校验任务依赖、列出可开展任务与写入冲突 |
| 设计与待实现工作 | 通用项目契约、FrameState、后端适配、风格等价、完整人物表演及长期生产调度 |

## 当前最短实施路径

21 项是工程积累清单，不是每部作品开拍前的必修课。北冥路线先复用现有 `createFilm / createLook` 做 T05 的固定场景小样；RAEA 路线从 T09 的独立 TSX 小样开始。先得到可验收的画面和动作，再处理实际遇到的共用问题。

只有出现同一镜头需要两后端执行时，才实施 FrameState 和跨后端适配；仅新增一个 TSX 作品不需要它们。项目/资产/结果先用文件记录，暂不建立新的调度服务、插件系统或通用 SDK 包装。共享 GPU 的占用协调、错误处理和交付检查仍要执行。

## 从需求到交付的顺序

1. **明确路线与视觉目标。** 要保持原片则选北冥风格路线；原生自由作品可直接选 RAEA。路线与后端分别记录。
2. **固定可比较输入。** 确认模型/底板/角色、相机尺度、时间、画幅和参考帧。没有这些，参数变化难以解释。
3. **先完成一个可见事件。** 一个明确的观看、抬头、接触或转身，比延长循环更能验证制作能力。
4. **逐层验证风格。** 反照率、灯光分档、阴影、轮廓、笔触、底板和显示层分开看。
5. **技术与创作分别验收。** 文件完整不代表动作已完成；画面好看也不代表工程能重建。
6. **保存证据再更新状态。** 记录源码版本、输入哈希、实际后端、命令、产物与未解决问题。

## 可直接执行的计划检查

```sh
npm run routes:check
npm run routes:next -- --route beiming
npm run routes:next -- --route raea
npm run test:routes
```

工具实现为 [tools/work-plan.mjs](../../tools/work-plan.mjs)，不依赖新 npm 包，不会自动开始任何渲染。它检查重复 ID、缺失依赖、依赖环、无证据完成、越界写入范围，以及可开展任务和已领取任务之间的写入冲突（包含已领取任务互相冲突）。路线筛选后仍会列出未完成前置的编号、路线和状态，方便转交跨路线依赖。

工具只检查证据记录是否存在，不判断截图/日志内容是否真实或合格；该项仍由集成者复核。发现冲突会在结果中列出，不会自动撤销其他代理的工作或强制接管文件。

受阻任务保留写入范围，不能因等待素材就把同一文件交给其他代理；需要移交时由集成人员先调整任务范围。路径比较按 Mac/Windows 共用工作区保守处理大小写和 Unicode 等价名称；它是词法提醒，不是文件锁，也不解析符号链接。

工作状态集中在 [work-plan.json](work-plan.json)。当前 T00（既有基线）与 T01（[项目与结果契约校验器](../../engine/production/project.js)）标记完成；T01 只做字段与路径校验，渲染器仍不读取项目记录。其余任务卡是下一阶段工程工作的细分，不是新功能已完成的声明。

修改任务清单时同步更新工作分解的任务卡，运行 `npm run test:routes`；测试会检查状态、依赖、负责人、写入范围和验收内容是否一致。

## 代理交付格式

每个子任务的返回至少包含：任务 ID、基线提交、实际变更文件、运行过的命令、产物路径、验收结果、未完成项。若某项只阅读源码，应写“源码核对”；若未在 Windows 执行，不写“5090 验证完成”。

共享入口和工作状态由集成负责人统一修改。局部指南中的 A/R/V 编号用于阅读，跨路线调度使用唯一的 T 编号。重叠写入任务必须串行或重新划分，不用恢复别人文件的方式解决冲突。
