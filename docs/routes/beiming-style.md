# 北冥风格路线：从现有源码到可复现的画风扩展

本路线保留北冥的美术和制作方法，再选择 Three 或未来的 RAEA 执行适配。风格来自造型、材质、照明、绘画底板、摄影、时间与后期共同作用，不是一个滤镜或一个渲染器名字。RAEA 可以提供场景、动作和原生执行能力；迁移后仍需逐层核对北冥的视觉目标。

本文核对仓库基线 `21ed1b10164a94a4fc0d7cf3973934d0f21f301f`。真实模块和默认值来自下列源码；建议实验与新增动作没有在本次渲染。通用 FrameState、风格版本管理和原生适配器仍为[待实现契约](contracts.md)。全局工程任务以 [T00–T20](work-plan.json) 为准，文末 A 编号只是本页实施步骤。

## 1. 先分清三层代码

| 层级 | 当前文件 | 应改什么 |
|---|---|---|
| 通用能力 | `engine/form`、`shade`、`paint`、`stage`、`look`、`overlay`、`render` | 复用的造型、着色、笔触、合成、时间与输出算法；修复这里会影响多个作品 |
| 北冥美术配方 | [`src/toon.js`](../../src/toon.js)、[`src/look.js`](../../src/look.js)、各鲲变体与二维人物 | 本片色板、材质族、造型、默认后期；新作品最好建立自己的配方文件 |
| 影片与镜头 | [`src/main.js`](../../src/main.js)、[`shotA`](../../src/shotA.js)、[`shotB`](../../src/shotB.js)、[`shotC`](../../src/shotC.js) | 时长、镜头切点、相机、对象状态及逐镜头参数覆盖 |

原片不是全三维城市：鲲和渡船是三维造型，天空、云、楼群和江面大量采用绘画底板；人物镜头由 Canvas 绘制人物，再放进合成场景。保留这种二维与三维的比例，是延续原片的重要条件。新增高精度模型可以增加空间和表演能力，但不会自动得到相同画风。

现有入口的调用链：

```text
src/main.js
  → createFilm({designHeight:1040})
  → 加载底板/字体、创建三个镜头、createLook(...)
  → film.run({dur:10, shots:[0,3,5], ...})
  → window.render(t)
  → 当前镜头.update(t,f)
  → 当前镜头.look(t)
  → 后期渲染 → 顶层二维显示画布
```

[`createFilm`](../../engine/stage/film.js) 设置 `DUR / render / READY / TEXTS`，预热后才开放渲染。当前镜头的 `update` 接收全局时间和帧号；镜头内部自行计算局部时间。改变这个约定必须同时改调用者与镜头，不能在新适配器中重复减镜头起点。

## 3. 色阶究竟怎样计算

原片的自定义着色不是简单给照片做亮度分层，也不只是默认 `gradientMap`。在 [`shadeGlsl`](../../engine/shade/toon.js) 中，法线 N、主光方向 L 和物体坐标噪声共同决定分档：

```text
hl  = 0.5 × dot(N,L) + 0.5 + 明暗边界噪声
hlS = hl × mix(1-shadowDepth, 1, 投影可见度)
m1  = 亮面与第一暗档的权重（基于 hlS）
m2  = 第一与第二暗档的权重（基于 hl）
色彩 = mix(亮档色, mix(第一暗档色, 第二暗档色, m2), m1)
```

羽化宽度同时考虑参数和 `fwidth`，减少像素边缘闪烁；投影还可以强制进入阴影档。之后再叠加天空冷光、下方暖光、背光侧与受光侧边缘光。主光主要提供方向和投影，颜色由本片色板明确给定。调灯强度不能代替调这套自定义颜色关系。

### 3.1 三种参数层级不能混为一谈

| 参数 | 引擎中性 `TOON_BASE` | 北冥 `TOON_DEFAULTS` | 鲲的 `TOON_PRESETS.kun` |
|---|---|---|---|
| 基色 | `#ffffff` | `#6E7BA8` | `#6E7BA8` |
| 第一/第二暗档 | 乘法色调 | 从原片暗色计算乘法色调 | 明确 `#4E5888 / #343D69` |
| `step1 / step2` | `0.55 / 0.30` | `0.56 / 0.32` | `0.53 / 0.17` |
| `feather1 / feather2` | `0.02 / 0.03` | `0.02 / 0.03` | 沿用默认 |
| `shadowLo / shadowHi` | `0.42 / 0.58` | 相同 | 沿用默认 |
| `fillAmt / skyAmt` | `0 / 0` | `0 / 0` | `0.92 / 0.75` |
| `rimAmt / rimLitAmt` | `1 / 0` | `1 / 0` | `0.6 / 1` |

来源分别是 [`engine/shade/toon.js`](../../engine/shade/toon.js) 与 [`src/toon.js`](../../src/toon.js)。`makeToonMaterial(opts)` 的对象覆盖值最终决定材质；运行时又可能直接改 `mat.userData.toon`。例如镜头 C 把对象的 `uFillStep / uFillStep2 / uFillW1 / uFillAmt` 改为默认 `0.38 / 0.72 / 0.5 / 1.0`，也开放了查询参数覆盖。因此复刻一帧必须记录镜头和时刻，不能只复制默认表。

原片关键色关系：天空 `#4F5BBF / #9C8FD8`，暖光 `#F2A0A6 / #FFB26B`，城市 `#4B4A8C`，墨线 `#2A2D52`。这些是色板输入；线性转换、补光、雾、调色和显示编码之后的最终像素不必等于输入十六进制值。

造型尺度也影响参数：原版 `createKun` 名义长度为 600，默认脊柱波幅 `uKunAmp=15`、波数 `uKunWave=0.8`、角频率 `uKunOmega=2π/5`，`lod` 限于 0.1–1。这些不是当前所有资产共同的米制标尺；迁移时要和导出鲲约 30m 的目标尺度明确转换。双色边缘光亮芯还要求材质族启用 `rimCore`，原版工厂不会因传入几个亮芯参数就自动增加该分支；已用该能力的例子见 [`toon_refine.js`](../../src/toon_refine.js)。

### 3.2 调什么会改变什么

| 控制 | 实际作用 | 实验时观察 |
|---|---|---|
| `step1 / step2` | 调两道明暗分界在半兰伯特域的位置 | 亮暗面积与体积转折；并非直接指定“几档” |
| `feather1 / feather2` | 调档位之间过渡宽度，仍受像素抗锯齿约束 | 从硬色块到较软体积；不是改几何精度 |
| `shade1/2`、`shade1/2Tint` | 明确阴影色或按反照率乘法着色 | 暗部色相、饱和度和材质统一；避免所有材质被染成同一种灰 |
| `shadowDepth / castShade / shadowLo / shadowHi` | 投影影响分档的深度、强制暗档和量化窗口 | 投影边缘与自身明暗是否同一视觉语言 |
| `edgeNoise / edgeNoiseScale` | 扰动明暗分界及相关计算 | 轮廓破碎是否来自受控笔触；缩放模型后频率是否变化 |
| `rim* / rimLit*` | 背光侧与受光侧硬边边缘光 | 轮廓识别、亮边宽度与位置；不应成为所有物体统一发光的贴边 |
| `fill* / sky*` | 定向暖补光与暗部天空冷光 | 环境与物体是否融入；避免误认为主光强度失效 |
| `patchScale / rust* / algae* / spot* / dab*` | 表面斑块、细点与植被斑驳 | 远景形体优先，近景细节不过密；同一物体随运动不漂纹 |

当前默认公式是三色混合，没有通用 `levels: N` 参数。需要真正不同的分档数或全新光照函数时，要改材质族的 `shade.bands` 等钩子或增加自己的实现，不能传入不存在的选项并宣称生效。

## 4. 墨线、笔触、颗粒与逐镜头参数

后期顺序由 [`engine/look/index.js`](../../engine/look/index.js) 固定：

```text
主场景：MSAA + HalfFloat HDR + 深度
ID/深度：检测边缘 → 生成笔画
场景雾 → bloom → grade → OutputPass
Kuwahara → 叠加墨线 → 纸纹 → 暗角 → 颗粒
顶层 HUD/字幕 Canvas
```

**检测先做、墨线后叠**，这样 Kuwahara 不会抹掉最终墨线。`look/ids.js` 的描边通道自行生成 ID/深度；它不是把 toon 材质的法线调试输出直接当作唯一输入。描边物体须带 `userData.outline`，顶点形变须同步到 `outlineVertex`，否则颜色、投影与线条会分离。

常用对象开关见 [`ids.js`](../../engine/look/ids.js)：`outlineWidth` 控制权重，`outlinePerInstance` 决定实例分别描边，`outlineGroup` 可合并内部 ID，`outlineOccluder` 区分实心/透明遮挡。底板不应被统一描成一个矩形外框。

[`src/look.js`](../../src/look.js) 默认线宽 2.6、墨色 `#2A2D52`、wobble 1.2、boilFps 12、pressure 0.35、breakup 0.1、inner 0.55；默认 Kuwahara 半径 5、强度 1、q 8；这些像素量按 **1080 高度标定**。正片则覆盖如下：

| 项目 | 镜头 A：0–3 秒 | 镜头 B：3–5 秒 | 镜头 C：5–10 秒 |
|---|---|---|---|
| 主体 | 雾江、渡船、远鲲 | 二维人物剪影 | 近鲲、云层与眼镜显示 |
| 屏幕墨线宽度 | 2.3 | 关闭，保留人物自绘轮廓 | 2.6 |
| Kuwahara 近/远半径 | 3 / 6.5 | 1.6 / 6 | 4 / 7 |
| 距离过渡 | 700–2200 | 30–60 | 900–3000 |
| 饱和度 | 1.10 | 1.08 | 1.10 |
| 暖度 | 0.12 | 0.13 | 0.12→0.20 |
| 纸纹强度 | 0.14 | 0.12 | 0.13 |
| 颗粒参数 | 0.65 | 0.65 | 0.65 |
| 暗角 | 0.24 | 0.26 | 0.24→0.16 |

上述值直接见各镜头 `look(t)`。颗粒 `0.65` 是 shader 输入量，**不是 65% 不透明度**。默认配置中的 `grain:0` 也不代表正片没加颗粒。镜头 C 末尾曝光和材质共享曝光均有时间变化，记录时应分别保存。

景别改变笔触半径是有意设计：人物面部不能被与远景云层相同的大半径抹平。放大输出时，设计摄影用 1040 高度坐标，后期按实际高度/1080 缩放，HUD 按实际高度/1040 缩放。不要通过提高设备像素比重复放大线宽。

## 5. 从参考图到新画风的实验流程

### 5.1 先把参考拆成可观察变量

为每组素材写一页视觉目标：主体亮暗面积、冷暖关系、阴影色、轮廓软硬、纹理尺度、雾与景深、二维/三维比例、镜头运动允许范围。图片可以支持静态美术判断；1–2 秒视频额外用于判断动作量化、纹理稳定和相机运动。单张图不能提供遮挡后的模型形体，也不能证明动画连续性。

### 5.2 先建校准场景，再生成变体

建议 T05 新建 `lab/style-calibration/`，固定种子、相机、灯位、曝光和输出尺寸，至少包含球/方体/曲面、有细节的主体、透明植被、底板和中文标题。这个目录目前是任务产物，本文没有生成它。

按以下顺序保存对照：

1. 灰模和轮廓：确认几何、法线、比例、遮挡及镜头。
2. 反照率：关后期，用同一套主体颜色核对材质。
3. 分档与投影：固定其他变量，调阈值、羽化和阴影关系。
4. 边缘光与表面纹理：分别检查亮边、锈斑、密度和尺度。
5. 底板、雾和空间：确认层次、视差、景别和透明边缘。
6. 笔触与显示：再调线宽、Kuwahara、纸纹与颗粒；最后加文字。

每个候选保存源提交、参数 JSON、资产哈希、相机/灯位、时刻与无损图。通过 `debug` 选择 `scene / id / depth / edge / line / bloom / kuwahara / paper` 检查中间结果；这些模式见 [`look/debug.js`](../../engine/look/debug.js)，部分是诊断显示，不是最终调色输出。

既有 [`lab/kun.js`](../../lab/kun.js) 使用临时描边，不能单独证明正片后期一致；[`lab/look.js`](../../lab/look.js) 使用测试几何和材质，也不能单独证明真实鲲材质一致。最后必须把选定配方放进同一个真实主体场景复核。可用现有静帧工具抽取原片基准（以下渲染命令本次未执行）：

```sh
node engine/render/still.mjs . 1.5 4 7.5 --size 1920x1040 --out out/style-baseline
```

### 5.3 40 张应是可解释的实验，而不是 40 个随机滤镜

以下是建议实验分配，**没有执行或宣称已得到 40 张新结果**：

| 组 | 数量 | 固定什么、改变什么 |
|---|---:|---|
| 色阶与羽化 | 12 | 固定色板与相机；不同分界位置 × 硬/中/软过渡，仍按当前三档公式 |
| 轮廓语言 | 8 | 固定选定材质；改变线宽、内部线比例、笔压与断线，保留无描边对照 |
| 表面语言 | 8 | 固定光照；调整斑块尺度/密度及远近细节预算 |
| 空间与笔触 | 8 | 固定主体；调整雾、近远笔触半径与纸纹强度 |
| 调色组合 | 4 | 对前面已通过的少数方案组合色板与环境补光 |

先比较单变量，再组合；每组保留一个共享基准。九张素材的景别和照明不同，不能分别挑九组互不相关参数后就称“统一风格”。先选代表性的室内人物、日景建筑和暮色水面验证同一个风格版本，再允许有记录的镜头级曝光/半径覆盖。

### 5.4 往 2D 或 3D 调整的边界

偏平面可减少体积渐变、简化内部线与表面高频、使用更明确的色块及绘画底板；偏立体可让几何转折、接触阴影、法线细节、相机视差和材质响应更明显。两者都保留三维结构时，属于三渲二的不同表达。只加深阴影不能把没有建模的照片变成三维场景；只减弱描边也不会自动变成 PBR。

风格版本应锁定规则，不要求每镜所有数值完全相同。允许调整的字段、范围和理由要写进版本记录；更换色板、光照公式或后期顺序应建立新版本并重做跨镜头对照。

## 6. RAEA 应接在哪几处

| 接入点 | 现在已有 | 下一步实施与验收 |
|---|---|---|
| 资产 | 自有 GLB 导出、验证与回读；RAEA 10 秒例片 | 保持单位、轴向、蒙皮/morph/clip；导出模型不包含原版屏幕墨线和后期 |
| 角色与动作 | 原片鲲的形变和眨眼；RAEA Model/Character 源码能力已研究 | 用真实角色资产验证动作、视线、手脚接触；不能把整体平移当作姿态变化 |
| 场景/时间 | 现有 Three 镜头与原生 TSX 分别可运行 | 北冥需要跨后端时先建最小 FrameState；原生自由作品不等待这一层 |
| 材质 | Three 自有分档、边缘光、表面层；原生 Toon 已有实验 | 将视觉目标映射为 WESL/原生材质，不机械复制同名参数。GLSL 不能直接当 WESL 执行 |
| 墨线/后期 | Three ID/深度墨线与 Kuwahara | 原生外壳描边只是另一种算法。北冥原生适配需单独验证 ID、深度、透明遮挡、后期顺序与色彩 |
| 执行 | 浏览器取帧和原生运行均有证据 | 对照同内容与实际编码器，再比较 GPU/CPU/读回/编码；不能把 Vulkan 等同于硬编码 |

完整来源、原生接口和限制见 [RAEA 源码对照](../raea/architecture.md)、[原生手册](raea-native.md)及[集成方案](../raea/integration.md)。独立 RAEA 例片证明资产与执行路径打通，不证明北冥原片已经风格等价迁移。

## 7. 用一个六秒事件验证表演与风格

以下是**建议的新镜头验收夹具**，未制作：24fps、144 帧，“她停下手中动作，察觉遮光，抬头看向鲲，鲲作出回应”。二维人物可以继续使用绘画姿态和分层动画，不要求先替换成写实三维人。

| 帧区间 | 可见变化 | 需要的数据与检查 |
|---|---|---|
| `[0,24)` | 手部动作减速并停住 | 明确起点、停点、接触位置；不能只把整张人物卡片冻结 |
| `[24,60)` | 阴影掠过，眼神先移，头部随后抬起 | 视线目标与头部姿态分别控制；面部轮廓、遮挡和眼镜位置随姿态改变 |
| `[60,108)` | 视线落到鲲眼，人物保持，鲲转眼或眨眼回应 | 世界目标映射到各镜头；动作的结果必须能从画面读出 |
| `[108,144)` | 回应结束，形成下一镜的稳定状态 | 角色时钟不归零；保留动作后的姿态与情绪，不重复开头动作 |

当前 `drawGirl` 不是通用二维骨架 API；需要在独立夹具里补关键姿态、遮挡层和部件变换。新动作参数不得写成现有引擎已导出的接口。连续摄影保持 24fps，鲲按三帧保持，人物可按两帧保持，但接触与视线求值仍须有明确时钟。

验收保留起点/峰值/终点、切点邻帧以及完整带声片段；评审“看到了什么变化”，不只评审“调用了什么函数”。先通过六秒，再扩为两事件的 30 秒段落；扩成更长影片时逐镜头保留这一标准。

### 7.1 已发现的姿态历史依赖

本次 CPU 检查复现了一个需要 T03/T04 处理的实际情况：[`kun.setPose`](../../src/kun.js) 在收到 `look` 后，将复用 Euler 的顺序改成 `YXZ`。新对象采样 `t=2`，再调用带 `look` 的 `t=3`，最后回到 `t=2`，两侧胸鳍四元数与首次采样的角差约为 **0.00025129346 / 0.00138398988 弧度**。它是状态差异；本次没有测量像素影响，也没有修改原片行为。

以下最小复现已在当前基线的 Node/Three 上执行，不启动 GPU；断言通过表示成功复现历史依赖，**不是确定性验收通过**：

```js
// 在仓库根使用 node --input-type=module 执行
import assert from 'node:assert/strict';
import * as THREE from 'three';
import { createKun } from './src/kun.js';
const kun = createKun({ lod: 0.1, wisps: false });
kun.setPose(2);
const before = kun.fins.map(f => f.pivot.quaternion.clone());
kun.setPose(3, { look: new THREE.Vector3(0, 0, -1000) });
kun.setPose(2);
const angles = kun.fins.map((f, i) => before[i].angleTo(f.pivot.quaternion));
assert.ok(Math.max(...angles) > 1e-5);
console.log(angles);
```

新状态层应显式规定每帧的旋转约定并做基准兼容，不能靠某个预热帧碰巧设置正确顺序。修复后重新比较旧片关键帧、顺序播放与跳帧；这也是不能仅凭 `render(t)` 接口就宣称任意作品可并行分段的原因。
