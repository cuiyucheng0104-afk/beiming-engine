# 取帧方式对比实验：截图与读画布

> 读者：想知道出片能不能靠换取帧方式提速、以及为什么现在没换的人与 agent｜状态：实测记录；实验脚本不在出片链路里，`engine/` 没有改｜依据：2026-11-17，提交 f49d43e，RTX 5090 工作站（Linux，ANGLE Vulkan）全量 240 帧，Mac M5 Pro（Metal）只跑了 24 帧冒烟；原始结果 [capture-experiment.json](capture-experiment.json)

出片链路现在是：无头浏览器逐帧截图（PNG 或 JPEG）→ Node 收 → 管道喂给 FFmpeg → 在 CPU 上换算成 YUV → x264 编码（[engine/render/README.md](../engine/render/README.md)「编码链」）。这份记录回答一个问题：改成「直接读画布像素、在显卡里转成 YUV、原始流喂给 FFmpeg」能快多少，画面还一不一样。

## 结论

- **能提速，幅度取决于并行路数。** RTX 5090 工作站上，显卡里转 YUV 再经本地 WebSocket 送出：单路快 2.5 倍，默认的 4 路快 1.7 倍，8 路只快 1.2 倍。
- **省下的主要是浏览器压 PNG 的时间。** FFmpeg 那一侧的 PNG 解码与色彩换算合计每帧只有一两毫秒，搬到显卡里几乎不省算力；转 YUV 的用处是把每帧数据从 8 MB 降到 3 MB，传出浏览器更快。只读 RGBA 不转 YUV，单路只快 1.3 倍。
- **路数多了以后瓶颈是 x264。** 8 路时各方式都停在每秒 50 到 60 帧。换显卡编码（h264_nvenc）能到每秒 60 帧，但码率与画质口径和现在的 x264 不是一回事。
- **读画布的 RGBA 与截图逐像素一致**，只在半透明叠加层的边缘有 0.14% 的像素差 1 级。**显卡里转的 YUV 与现有换算链不一致**：亮度最多差 1 级，色度最多差 6 级。
- **先不接入出片链路**（2026-11-17 的决定）。这份记录和脚本留作依据，要接入时的前提见「要接入的话」。

## 测了什么

脚本是 `tools/rtx/capture-bench.mjs`。同一部片（《北冥》10 秒样片，240 帧，1920×1040，24 帧/秒），每种方式都用同样的 x264 参数（crf 14、preset medium）编码，只算取帧加编码的用时，不含起浏览器与预热；每项跑两遍取较快的一遍。

| 方法 | 做法 |
|---|---|
| `png` | 现在的无损路径：截图成 PNG，FFmpeg 解码并换算 |
| `jpeg` | 现有的有损路径：截图成 JPEG（质量 95） |
| `rgba-b64`、`rgba-ws` | 页内把 WebGL 画布与叠加层画布合成后整帧读回 RGBA，FFmpeg 按原样换算 |
| `nv12-b64`、`nv12-ws` | 合成后在显卡里按有限范围 BT.709 转成 NV12（色度 2×2 平均）再读回，FFmpeg 不再换算 |
| `nv12-ws-nvenc` | 同上，编码器换成 h264_nvenc（`-cq 16`） |
| `png-again` | `png` 原样再跑一遍，用来看同一路径两遍是否一致 |

`b64` 是把像素经调试通道（base64）传出浏览器，`ws` 是经本地 WebSocket 传出。还试过用 HTTP 上传传像素（没入库的早期版本）：RGBA 每帧 394 毫秒、YUV 每帧 166 毫秒，比截图还慢，已去掉。

## 计时（RTX 5090 工作站）

单路，240 帧：

| 方法 | 用时 | 帧/秒 | 每帧取帧 | 相对 `png` |
|---|---|---|---|---|
| `png` | 24.91 秒 | 9.6 | 100.3 毫秒 | 1 倍 |
| `jpeg` | 13.68 秒 | 17.5 | 54.1 毫秒 | 1.8 倍 |
| `rgba-b64` | 21.03 秒 | 11.4 | 85.0 毫秒 | 1.2 倍 |
| `rgba-ws` | 19.25 秒 | 12.5 | 77.5 毫秒 | 1.3 倍 |
| `nv12-b64` | 11.07 秒 | 21.7 | 43.7 毫秒 | 2.3 倍 |
| `nv12-ws` | 9.83 秒 | 24.4 | 38.6 毫秒 | 2.5 倍 |
| `nv12-ws-nvenc` | 8.65 秒 | 27.8 | 35.4 毫秒 | 2.9 倍 |

多路并行，总帧/秒（括号里是相对同路数 `png` 的倍数）：

| 路数 | `png` | `jpeg` | `rgba-ws` | `nv12-ws` | `nv12-ws-nvenc` |
|---|---|---|---|---|---|
| 4 | 29.1 | 46.7（1.6） | 31.8（1.1） | 50.7（1.7） | 62.0（2.1） |
| 8 | 43.8 | 57.6（1.3） | 32.5（0.7） | 52.7（1.2） | 60.0（1.4） |

其他数字：

- 页内纯读回（不含传出浏览器）：RGBA 4.7 毫秒，NV12 3.7 毫秒。
- 起浏览器：第一路 1.62 秒，另外 7 路一起 3.18 秒；预热 3.09 秒。
- 作为参照，同一台工作站按提交 99e1767 正式出这部样片，整条命令约 65 秒，其中渲染加编码 12.84 秒（4 路，含起浏览器）。对这部 10 秒片，换取帧方式最多省 4 秒左右。
- Mac M5 Pro（Metal，24 帧冒烟）：`png` 每帧 83.5 毫秒，`nv12-ws` 每帧 62.0 毫秒，约 1.3 倍。Mac 上页内读回要 38 到 64 毫秒，慢在跨上下文把画布拷成纹理。

工作站是共用的，别的任务会把数字带偏：同一脚本在 1 分钟负载约 42 时跑过一轮，`nv12-ws` 单路从 9.83 秒变成 14.55 秒，4 路从 4.74 秒变成 8.65 秒。所以结果里记了运行前后的负载（`info.loadBefore`、`info.loadAfter`）。上表这一轮开始前处理器 99% 空闲、显卡占用 5%（`loadBefore` 的 16.5 是前一个任务留下的平均值，还没降下来）；临近结束时别人的任务又起来了，8 路那几项可能略受影响。此前用入库前的脚本在空闲时跑过两轮，各项与上表相差在一成以内。

## 画面一致性

同一次渲染下，截图对读画布（抽第 30、120、200 帧）：

| 帧 | RGBA 与截图不同的像素 | NV12 亮度不同的样本 | NV12 色度不同的样本 |
|---|---|---|---|
| 30 | 0 | 4.2%，最多差 1 级 | 11.0%，最多差 6 级，平均 0.12 级 |
| 120 | 0 | 4.3%，最多差 1 级 | 5.9%，最多差 3 级，平均 0.06 级 |
| 200 | 0.14%，最多差 1 级 | 4.9%，最多差 1 级 | 12.9%，最多差 5 级，平均 0.14 级 |

- 第 200 帧有半透明的叠加层（片名），差的那 1 级出在合成的舍入上：浏览器按 8 位算，实验里的着色器按浮点算。
- NV12 的参照是「截图 PNG 经现有换算链」的结果。色度差得多，是因为下采样的滤波不同（实验里是 2×2 平均）。要对齐得照 FFmpeg 的滤波与色度取样位置重写这一步。
- 成片层面，`jpeg` 与 `png` 的 PSNR 是 41.8 dB，`nv12-ws` 是 43.9 dB，`rgba-ws` 是 45.9 dB；而 `png` 自己跑两遍之间也只有 46.6 dB（见下一节），所以 RGBA 路径与截图路径的差别落在基线自身的波动之内。

## 顺带发现：工作站上同一帧渲两遍不一致

这不是新方法带来的，但它决定了在这台工作站上没法用「逐像素相同」验收任何取帧方式：

- 第 200 帧连渲两次，有 219 个像素不同，最多差 23 级；第 30、120 帧两次一致。
- `png` 路径原样跑两遍，240 帧里 145 帧的解码结果不同。
- 两次正式出片（提交 99e1767）的工作版视频逐帧比对，240 帧里 129 帧不同，第一处在第 73 帧。
- Mac 上只核对过前 48 帧，两遍一致。

原因没有查。复查方法：`ffmpeg -i <视频> -map 0:v -f framemd5 -` 逐帧出哈希后比对。

## 要接入的话

没有接入，原因和前提是同一组事：

1. **色彩链要重新认证。** 金标准与 QA 的色彩检查建立在「截图 → FFmpeg 换算」上。显卡里转 YUV 要么把滤波对齐到逐级一致，要么按 [画面基线的审批流程](style-baselines/POLICY.md) 重新认可。
2. **只适用于画面全在画布上的页面。** 实验合成的是一张 WebGL 画布加一张 2D 叠加层画布（`engine/stage/film.js` 建出来的结构）。C 路线的页面型动画有 DOM、SVG、CSS，读画布会丢层，截图才拍得全。这一类没有测。
3. **路数多了收益小。** 8 路时只快 1.2 倍。想再往上要换编码器，那是另一个交付口径。
4. **传输通道要换成正式依赖。** 实验里的 WebSocket 服务端借用了 playwright-core 打包在内部的模块，不是公开接口。
5. **多一条要维护的路径。** 合成着色器、YUV 换算、传输通道都是新代码，而现有的 `jpeg` 路径已经有 1.6 到 1.8 倍。

比较稳妥的接法是做成 A 路线工作版的可选快速通道，终渲与金标准继续走 PNG。这只是建议，没有排进工程计划。

## 复现

```sh
# 本机
node tools/rtx/capture-bench.mjs . --frames 240 --reps 2 --lanes 1,4,8
# 从控制机派到工作站（机器档案见 tools/remote/README.md）
node tools/remote/cli.mjs run <机器> --fetch out/capture-bench/results.json -- node tools/rtx/capture-bench.mjs . --frames 240 --reps 2 --lanes 1,4,8
```

结果是一个 JSON 对象（同时写到 `out/capture-bench/results.json`），各方式的成片也留在 `out/capture-bench/`，不提交。

## 没测的

- 只测了《北冥》样片这一部片；别的作品、4K、C 路线都没测。
- 取帧每帧 38.6 毫秒里，渲染、传输、等编码各占多少没有拆开。
- Windows 没有跑；Mac 只有 24 帧冒烟，没有全量。
- 正式出片整条命令 65 秒里，除渲染外的混音、QA 各占多少没有拆。
