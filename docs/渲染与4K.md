# 渲染与 4K

> 读者：要出 4K 成片、比较画质与速度、在工作站上排渲染的人与 agent｜状态：渲染器口径已按 v2 更新（2026-11-10）；画质与计时是 2026-11-04 的实测记录｜依据：RTX 5090 工作站与 Mac M5 Pro 的实测；渲染器规格见 [engine/render/README.md](../engine/render/README.md)

《北冥》样片的 4K 实测：原生 4K、RTX 超分、普通放大三种路线的画质对比，两台设备的渲染计时，以及跨平台画面一致性；最后是现在怎么出 4K、要注意什么。

## 结论

**出片用原生 4K，不用 RTX 超分。**

- 原生 4K 画面最好：代码画的墨线、形体、纸纹都按 4K 像素重新计算，干净细腻。
- 原生 4K 也更快：RTX 5090 工作站上约 31 秒，Mac M5 Pro 上约 51 秒（2026-11-04 的计时，见下文“计时”）。
- RTX 超分端到端约 3 分钟，并且会在大块平涂区凭空生成蚯蚓状纹理，破坏手绘纸感。
- **但绘画底板是固定分辨率的位图**：4K 下会被放大，见“4K 下的绘画底板”。原生 4K 只解决“代码画的部分”。

## 现在怎么出 4K（渲染器 v2）

```sh
node tools/rtx/gpucheck.mjs                                                     # ★ 后端要落在硬件 GPU 上
node engine/render/video.mjs . --size 3840x2080 --plan                          # 《北冥》4K：先估算耗时与磁盘
node engine/render/video.mjs . --size 3840x2080 --workers 8 --out out/video_4k.mp4   # 即 npm run video:4k
node engine/render/video.mjs films/<名字> --profile uhd-2160p24                 # 新作品：交付档位 3840×2160 24 fps
```

PowerShell 设环境变量的写法是 `$env:BEIMING_ANGLE = 'vulkan'`，bash 是 `BEIMING_ANGLE=vulkan node …`。

- **浏览器**：渲染器用 Playwright 自带、`package.json` 锁定的 chromium-headless-shell（playwright-core 1.63.0 对应的 headless shell 153，决定 D09）。`npm run setup` 安装，`npm run env:doctor` 与 `node tools/rtx/gpucheck.mjs` 用的是同一个浏览器和同一组启动参数，看到的就是渲染时的 GPU。不要用系统 Chrome 的版本号当环境口径。
- **GPU 后端**：Windows 默认 `vulkan`（`default` 在多显卡机器上可能选中核显），macOS `metal`，Linux `default`。写错或平台不对的 `BEIMING_ANGLE` 直接报错退出 2，不再静默落到软件渲染；`--gpu required`（默认）时落到 SwiftShader / WARP 退出 3。
- **中间帧**：每帧截无损 PNG，FFmpeg 只做一次色彩换算（有限范围 BT.709，写明三项标记）编成 H.264；`--fast` 改用 JPEG 中间帧，只用于预览。4K PNG 截图比 JPEG 慢，用 `--plan` 先量。
- **共用工作站**：设 `RENDER_SLOTS` 限制整台机器同时渲染的路数；有 `nvidia-smi` 时开渲前查共享 GPU（占用率、空闲显存、ComfyUI 队列），忙就排队，从不终止别人的任务。
- **成片**：`node engine/render/lib/mux.mjs`（或兼容壳 `sh engine/render/mux.sh`）封装：画面已是完整标记的 BT.709 时原样拷贝、只编码音频；响度按 BS.1770 实测线性归一到 −14 LUFS，真峰值 ≤ −1.0 dBTP。

## 4K 下的绘画底板

`assets/plates/` 的 13 张绘画底板（AI 生成后人工整理，来源见 `assets/plates/plates.json`）宽 3072–4344 像素，在镜头里只占画面的一部分并且随推拉放大，所以 4K 输出时屏幕上每个像素分到的底板像素不到 1：审计实测相对原图放大约 2.6–3.5 倍（GAP-03）。表现是天空、云、城市剪影比代码画的墨线软，细节不随分辨率增加。

- 交付 4K 前跑 QA 门的底板检查：`node tools/qa/cli.mjs plates --page <作品目录> --size 3840x2160`。贴图密度低于 1.0 texel/px 报注意，低于 0.6 不通过（阈值见 docs/quality/QA-GATE.md）。
- 要真正的 4K 画质，底板要按镜头里的最大放大率重新生成或放大到足够分辨率，再更新 `plates.json` 的来源记录；不要指望渲染分辨率替底板补细节。
- 纸纹 `paper.png` 是 1024×1024 的平铺纹理，不受影响。

## 测试条件（2026-11-04）

- 样片 10.0 秒，24 fps，共 240 帧。两台机器渲染同一份工程，文件逐一校验一致。
- 当时的编码链：JPEG 中间帧 → H.264 crf 14，色彩标记不完整（全范围、BT.601 矩阵）；封装时再以 crf 19 重编码一次，成片响度约 −14.9 LUFS。**这三点在 62ad28e 与渲染器 v2 里都已改正**：现在是有限范围 BT.709 并完整标注、封装拷贝画面不再多一代有损、成片 −14.0 LUFS（实测 I −14.0 LUFS、LRA 8.2 LU、真峰值 −1.6 dBTP）。下面的画质对比结论不受影响，计时与逐像素数字要用新链路重测。
- 颗粒已在页面里画在显示层下方，封装时不再叠加。

三个对比版本：

| 版本 | 做法 |
|---|---|
| 原生 4K | 引擎直接按 3840×2080 渲染 |
| RTX 超分 | 1080 渲染，经 RTX Video Super Resolution（ULTRA，×2）放大到 4K |
| 普通放大 | 1080 渲染，lanczos 放大到 4K |

## 计时（2026-11-04）

单位为秒，各设备取最好成绩。当时的中间帧是 JPEG；现在默认无损 PNG，单帧截图更慢，出片前用 `node engine/render/video.mjs <目录> --plan` 实测估算（试渲 8 帧并真编一遍，给出总时长与磁盘占用）。`gpucheck.mjs` 的着色器微基准只说明 GPU 着色快慢，不是出片吞吐。

| 任务 | Mac（M5 Pro） | RTX 5090 工作站 |
|---|---|---|
| 1080 渲染 | **10.9**（4 worker） | 13.1（6 worker） |
| 原生 4K 渲染 | 50.8（4 worker） | **31.4**（10 worker） |
| 4K 单帧 | 0.21 | 0.13 |
| RTX 超分 1080→4K | 不支持 | 约 184 |
| 封装（混音 + 两遍响度） | — | 1080 为 7.3，4K 为 25.1 |

- 1080 时 Mac 反而快，工作站多出的几秒花在启动 Chrome 上。
- 4K 时工作站快约 1.6 倍。加 worker 帮助不大，6 个到 10 个只快了 2 秒。成片与 worker 数无关（块的边界固定），路数只影响速度。
- 工作站跑 4K（6 worker）：GPU 平均占用 46%，最高 82%；显存最高 18.8 GB；功耗平均 108 W。
- 超分慢在 PNG 读写，不在模型。模型每帧只要 0.017 秒，240 张 4K PNG 的存盘却花了 135 秒。
- 现在的封装在画面已完整标记时直接拷贝视频轨，4K 封装不再花 25 秒重编码。
- Mac 计时时机器上还有其他任务在跑，数字偏保守。

## 跨平台一致性（2026-11-04）

Mac 与 RTX 工作站渲出的画面一致。

| 比对 | 结果 |
|---|---|
| 无损截图，1080，5 个时刻 | 完全相同的像素 58–76%；差超过 2 个色阶的像素 0.5–3.6%；PSNR 43–51 dB |
| 视频，1080，240 帧 | SSIM 0.9715（逐帧最低 0.9635），PSNR 41.1 dB |
| 视频，原生 4K，240 帧 | SSIM 0.9733，PSNR 41.5 dB |

差异几乎全部集中在显示层的文字边缘，另有零星墨线像素。原因是 macOS 与 Windows 的文字光栅化方式不同，肉眼看不出区别。没有文字的画面，差异只有 1–2 个色阶。所以同平台的回归比较用逐像素一致，跨平台用容差（金标准工具 `tools/baseline` 按这个口径）。

## 原生 4K、RTX 超分与普通放大

以下为 1:1 像素对比。

| 看什么 | 原生 4K | RTX 超分 | 普通放大 |
|---|---|---|---|
| 显示层小字 | 细，边缘干净 | 锐，但笔画略粗、带一圈亮边 | 发软 |
| 墨线（藤壶、眼镜、船） | 细而连贯 | 锐利 | 发糊，有台阶 |
| 平涂区（人物剪影、深蓝背景、纸面） | 纸纹细腻 | **凭空长出蚯蚓状纹理**，像过度锐化的油画 | 颗粒被放大成块 |
| 绘画底板（天空、云、城市剪影） | 与普通放大接近（底板本身分辨率不够，见上文） | 锐化出假细节 | 发软 |
| 构图 | 与 1080 完全一致 | 与 1080 一致 | 与 1080 一致 |

关于逐像素指标：成片每帧都有逐像素颗粒，原生 4K 的颗粒是按 4K 像素重新生成的一组噪声。三组 SSIM 因此都只有 0.72–0.77，主要是在比颗粒，不反映清晰度。画质结论以 1:1 对比为准。

| 比对 | SSIM |
|---|---|
| 超分对原生 4K | 0.722 |
| 普通放大对原生 4K | 0.748 |
| 原生 4K 缩回 1080 对原生 1080 | 0.767 |

## 引擎如何支持原生 4K

镜头按 1040 高的设计尺寸摆位；渲染器、后期和显示层用实际像素，镜头交给显示层的屏幕坐标乘上相应倍率。这样同一套镜头设定在任何分辨率下构图一致，1080 下的输出与改动前逐像素相同。渲染器把实际画幅、帧率与交付档位注入页面的 `window.__RENDER`（页面约定 v1），页面不必自己猜。

## 建议

1. 出片用原生 4K。交付前先 `--plan` 估算，再跑 QA 门的底板密度检查。
2. 日常迭代渲 1080 就够，十来秒一轮。4K 只在出片时渲。
3. 4K 交付要求底板也是 4K 质量时，先按镜头最大放大率补底板分辨率。
4. RTX 超分留给拿不到原生分辨率的素材，例如 AI 生成的视频镜头。若要用，先把逐帧读写改为显存内直通，否则大部分时间耗在存盘上。
5. 换了模型、场景或渲染链路后，渲染负载会变，计时需要重测。
