## 1 多平面原理

### 1.1 三种做视差的方法

| 方法 | 原理 | 仓库里的位置 |
|---|---|---|
| 真实透视（在三维里摆面片） | 底板是三维场景里的面片，相机真的移动，视差由透视自然产生 | 镜头 A、C。【仓库实证】src/shotA.js:3；engine/stage/camera.js:2 |
| 二维系数（各层按系数缩放、平移） | 相机不动。每层按"相机推进量 × 本层系数"在二维平面里缩放或平移 | 镜头 B 的天空只推人物推进量的 30%（src/shotB.js:34-41；src/girl.js:24, 363-366）；光尘按 `0.6 + 深度` 的系数推（src/girl.js:617）。C 路线的例子见 §7 |
| 深度图位移（照片浮雕、原画分层） | 给一张图配一张深度图，按深度把像素局部位移；相机做小幅推移或平移时产生视差 | C 路线：`cases/source/ppt-jianlong/jianlong/tools/depth.py:1-8`（手工多边形由远到近分层，可与单目深度估计的结果按 0.5/0.5 融合，再以原图灰度做引导滤波让深度边缘贴住画面）；`cases/source/ppt-jianlong/jianlong/src/core/plates.js:1-3`（每张图版配一张深度图 `dNN`）；`cases/source/ppt-understands-you/tools/depth_render.py:1-8`（手工深度规格：地面渐变＋由远到近覆盖的多边形与椭圆）。A 路线没有这种做法【未实现】 |

真实透视的好处是遮挡关系、视差方向和推镜放大都能自动对上，也能和三维物体放在同一个空间里。二维系数法成本低、好控制，但视差的方向和大小全靠人来保证（失败模式见 §5"视差方向错误"）。

深度图位移适合"只有一张图"的素材：PPT 原画、照片、插画转片。仓库流程写明了它的边界：单张图片估计出的深度只支持受限机位，不能声称已经补全背面（`docs/cases/ppt-animation.md:48`）。【通用工艺】位移一大，深度跳变的边缘会拉丝，前景物体的背后没有画面内容；所以机位只做小幅推移，或者把前景抠成单独一层、背后补画。PPT 或原画转片的完整开工顺序见 `docs/cases/ppt-animation.md` 与 `docs/cases/comparison.md:66-70`。

### 1.2 按屏幕像素 + 视线深度摆面片

`placeOnScreen(mesh, cam, W, H, cx, cy, wpx, D, hpx)` 在**起始机位**下完成摆放（engine/stage/camera.js:30-38）：

```
hh = D·tan(fov/2)，hw = hh·aspect            // 深度 D 处的半画高、半画宽（米）
x = (cx/W − 0.5)·2·hw，y = (0.5 − cy/H)·2·hh   // 屏幕像素换算成相机坐标
w = wpx/W·2·hw，h = hpx/H·2·hh                 // 不给 hpx 时，h = w / 贴图宽高比
面片位置 = 相机坐标 (x, y, −D) 变换到世界；朝向 = 相机朝向；缩放 = (w, h)
```

【仓库实证】由此可知：t0 时刻，面片正好盖住设计稿上那块像素矩形，**和 D 无关**。D 只决定两件事：一是之后怎么动（平移视差与 1/D 成正比，推镜放大倍数为 D/(D − 推进量)）；二是它和三维物体谁挡谁（靠深度测试）。所以 A 路线的做法是：先在 1920×1040 的设计稿上排好版（`designHeight 1040`，src/main.js:19-20；engine/stage/film.js:3-4），再给每一层分配 D 来调视差。

相关函数（头注释见 camera.js:1-14）：

- `fillScreen`（camera.js:39）：在深度 D 处铺满画面。如果每帧都用当前相机来摆，这一层就锁定在屏幕上，没有视差。例子：镜头 B 的背景层和人物层（src/shotB.js:21, 23），镜头 A 每帧重摆的鸽群层（src/shotA.js:140）。
- `placeStrip`（camera.js:40-46）：把面片摆成从世界点 a 到 b 的一条屏幕条带。尾迹每帧都用船头和船尾的世界坐标重新生成（src/shotA.js:118-124），所以这条二维笔触画的尾迹会跟着三维的船走。
- `screenToWorld`（camera.js:48-51）和 `screenToPlane`（camera.js:53-56）：把三维物体锚到二维构图上。鲲放在屏幕 (1180, 236)、深 2900 m 处（src/shotA.js:63-64）；渡船放在屏幕 (800, 742) 这条视线与水面 y=0 的交点上（src/shotA.js:80）。【仓库实证·复算】这个交点离相机 931 m，沿视轴的深度是 928 m。
- 镜头 C 的前景云墙用 t=5.0 时的**克隆相机** `cam0` 来摆（src/shotC.js:61-62, 73-74）。之后真实相机跟着渡船前移、微晃，云墙作为世界里固定的平面就会产生视差。如果误用实时相机 `cam` 去摆，云墙就会"粘在镜头上"，完全没有视差。

### 1.3 分层规划（从远到近）

【通用工艺】经典的多平面一般分五带：天幕（没有视差）→ 远景（定地平线，视差弱）→ 中景（主体所在的空间）→ 近景（提供尺度参照，视差明显）→ 前景遮挡（框住画面、引导视线，视差最大）。相邻两带的**深度比**决定层次感；同一带里几层的深度比较接近，看起来就会"压"成一体。

**穹顶面片**（engine/stage/dome.js）：

- 映射关系：u 映射到水平角 `yaw = yawC + yawSpan·(0.5 − u)`（向左为正），v 映射到仰角 `lerp(pitchLo, pitchHi, v)`（dome.js:15-18）。贴图的左右、上下和画面方向一致（dome.js:4）。
- 为什么用穹顶：平面底板一摇镜头就会透视变形、露出边缘；以相机为球心的球面在摇镜、仰拍时"不变形、不穿帮"（dome.js:1-3）。穹顶组挂在相机位置上，就没有平移视差（适合天空）；挂在附近的固定点上，会有少量视差（适合云堤、天际线）（dome.js:2；src/shotC.js:43-47）。
- 【仓库实证·复算 + 渲染】按穹顶映射算，t=9.9 时东方明珠塔尖应在屏幕 (1408, 497)；用仓库渲染器出的静帧里，它在 x≈1415。

### 1.4 空气透视按深度分层

仓库用三套机制分别处理三类对象。

**① 底板：空气透视直接画进去。** 越远越浅、越偏雾紫、对比越低。底板材质设成 `fog:false, toneMapped:false`（engine/stage/plates.js:28-31），不吃场景雾，否则会被雾再灰一遍。

**② 三维物体：用场景指数雾 FogExp2，雾色取底板色板里的紫。** 镜头 A 用 `#A99BD9`、密度 0.000195（src/shotA.js:18）；镜头 C 用 `#B8A6DD`、密度 0.00085（src/shotC.js:22）。对照色板里的"薰衣草 #9C8FD8"（assets/plates/plates.json:16），后期的默认雾色也是同一支紫（src/look.js:19）。three r170 的 FogExp2 雾量公式是 `1 − exp(−(密度·视深)²)`（node_modules/three/src/renderers/shaders/ShaderChunk/fog_fragment.glsl.js:6）。【仓库实证·复算】镜头 A：鲲在 2914 m 处雾量 27.4%，渡船在 928 m 处 3.2%，所以远处的鲲被雾吃进云里，近处的船依然清楚。镜头 C：130 m 处 1.2%，600 m 处 22.9%，1000 m 处 51.4%。

**③ 墨线和笔触也随深度变化。**

- 墨线的 near/far/farScale：镜头 A 从 300 m 到 3000 m 线宽降到 0.6 倍（src/shotA.js:147）；镜头 C 从 90 m 到 700 m 降到 0.55 倍（src/shotC.js:205）。远景鲲的墨线整体透明度压到 0.5（src/shotA.js:60；engine/stage/outline.js:22）。
- Kuwahara 笔触半径按深度从 radius 过渡到 farRadius（engine/look/kuwahara.js:29-34）：镜头 A 在 700 m 到 2200 m 之间，从 3 px 过渡到 6.5 px（src/shotA.js:148）。

**屏幕空间雾**（engine/look/fog.js）三个镜头都关着（`fog: null`，见 src/shotA.js:151、src/shotB.js:63、src/shotC.js:209、src/look.js:44）。它根据深度缓冲重建距离（fog.js:51-57），而底板不写深度。【推断】如果打开它，底板像素会按"它背后那个三维物体，或者清屏"的深度加雾：前景云片盖在鲲上的地方，会出现鲲形状的雾量差。fog.js 为此留了两个参数：`cutoff`（超过这个距离的不加雾，给远处底板留原色）和 `sky`（清屏处的雾浓度）（fog.js:9-14, 22-28）。它只在以三维为主的场景里用过，见自测配置 lab/look.js:233。

【通用工艺】空气透视随距离增加的分层原则：① 明度向雾色收拢；② 饱和度下降；③ 色相向天光色偏移；④ 对比和细节减少；⑤ 边缘变软。最深的暗部和最亮的高光留给前景，远层不能出现比近层更黑的黑。北冥由冷到暖的色板（docs/作品.md:55-63）也要按深度执行：近层可以更饱和，远层更接近天空色。

### 1.5 renderOrder 与深度写入

【仓库实证】底板材质是透明的，`depthWrite:false`，`depthTest` 保持默认的 true（engine/stage/plates.js:29-31）。three@0.170.0（package.json:26）先画不透明物体，再把透明物体按"renderOrder → 距离"排序后画（node_modules/three/src/renderers/webgl/WebGLRenderLists.js:27-45）。这带来三条规律：

- **底板和底板之间谁盖谁，只看 renderOrder**，也就是画家算法。
- **底板和三维物体之间谁盖谁，看深度测试。** 不透明的鲲先画，并写入深度；D 比鲲远的底板在鲲所在的像素上测试失败，被挡住；D 比鲲近的底板则盖在鲲上。镜头 A 的鲲就这样夹在 clouds_back（6000 m）和 veil（2500 m）、clouds_front_a（2300 m）之间（src/shotA.js:2-4, 27-32, 63）。【仓库实证·渲染】t=2.95 的静帧里，鲲背从云上方露出来，并且被 D=1500 的天际线（上海中心）正确地挡住。
- 所以 **D 和 renderOrder 必须同序**：越远，order 越小。否则视差说它在后面、绘制顺序却说它在前面，相机一动观众就会察觉。镜头 A 的所有层都是同序的（见 §1.3 表）。

其他细节：

- 透明的"三维附属物"也插在底板的顺序里。尾迹 5.2、灯影 5.3，压在低雾 5 之上（src/shotA.js:71, 78）；它们在 ferry.js 里的缺省值是 4.8 和 4.9（src/ferry.js:106, 131）。
- plates.json 里的"层级"字段（assets/plates/plates.json:13，例如外滩 5、低雾 5.5）和镜头 A 实际的 renderOrder（低雾 5、外滩 6、近雾 6.5）不一样。代码并不读这个字段：plates.js 只读 name 和 url（engine/stage/plates.js:15-20），main.js 也只取 tex（src/main.js:27）。以代码为准，登记表需要更新。
- 描边与遮挡：底板设了 `userData.outline=false`（plates.js:33），所以不会被描成一个矩形框。在 ID 图里，透明材质会自动按"自身 alpha 半挡"处理（engine/look/ids.js:14-15, 131-139）：云片盖住鲲的地方，鲲的墨线按云片的 alpha 变淡，而不是穿过云片画出来。lab/look.js:202-216 专门测试了这一点。抠像面片的深度遮罩不参与挡线（`outlineOccluder=false`，plates.js:82）。

### 1.6 抠像面片：靠深度遮罩让笔触按距离变粗细

`cutoutPlane(tex, {order, cut})`（engine/stage/plates.js:77-86）其实是两张叠在同一位置的面片：

- **彩色层**：透明混合，不写深度，所以边缘柔和。
- **遮罩层**：`alphaTest = cut`、`colorWrite:false`、`depthWrite:true`，renderOrder 是 order − 0.5。它没有设 transparent，所以进入不透明队列，会先写深度。

后期先把主场景渲到一张带深度纹理的 HDR 目标上（engine/look/index.js:81, 108-109）。Kuwahara 读这张深度纹理，按 `rad = mix(radius, farRadius, smoothstep(farStart, farEnd, z))` 计算笔触半径，清屏处的 z 记为 1e9（kuwahara.js:29-34）。半径还会按"输出高度 / 1080"缩放（kuwahara.js:79；index.js:93）。

【仓库实证·复算】以镜头 B 为例：

- 人物层的遮罩在 D=10，z=10 小于 farStart 30，所以笔触半径是 1.6 px。
- 天空层虽然用 `fillScreen` 摆在 D=100，但它不写深度，深度缓冲在这里是清屏值，所以拿到 farRadius 6 px（src/shotB.js:19-23, 60）。
- 原生 4K 时，两个半径都再乘 2。

结果是人物用细笔触，天空用大笔触。【仓库实证·渲染】t=4.0 的静帧里，侧脸和镜框边缘很利，天空是大块平涂加纸纹。镜头 A 的鸽群遮罩在 D=30（src/shotA.js:86, 140），对应半径 3 px。

由此可推出一条规则（【仓库实证】+【推断】）：普通的 `plate` 不写深度，所以**它的笔触粗细取决于它背后有什么**。背后是鲲，就用鲲的距离算；背后什么都没有，就用 farRadius。

- 想让一张手绘前景底板得到"近处的细笔触"，要用 cutoutPlane，不能用 plate。
- 反过来，想让三维物体融进底板的大笔触，就把它放到 farStart 以外。镜头 A 的鲲在 2914 m，已经超过 farEnd 2200 m，所以和底板一样是 6.5 px。

## 2 底板规格（给出图或手绘的人）

### 2.1 出血（过扫描）：公式与算例

**符号**

- 设计画面 W×H = 1920×1040。焦距 f = (H/2)/tan(fov/2)，fov 是竖直视场（three 的 PerspectiveCamera 约定）。
- 一段镜头里，相机相对 t0 机位、在 t0 相机坐标系里的最大位移：横移 Tx、升降 Ty、前推 Tz（向前为正）。最大转角：水平摇 Δψ、俯仰 Δθ。
- 这一层在 t0 时的视深是 D。放大倍数 m = D/(D − Tz)：推镜时 m > 1，拉镜时 m < 1。
- a 是该层必须盖住的那条画框边，到推镜扩张中心的距离（像素）。沿视轴推镜时扩张中心就是画面中心，所以左右边 a = W/2；上下边 a = H/2。如果推进方向偏离视轴，要按实际的扩张中心来算。

**公式**（每条边需要画到画框外的量，单位是 t0 画面像素）：

```
o = f·|T⊥|/D + f·tan|Δ转角| − a·(1 − 1/m)
```

- T⊥ 是垂直于这条边的平移分量：左右边用 Tx，上下边用 Ty。
- 推镜（m > 1）时，最后一项是"扩张抵扣"，可以少画一些。拉镜（m < 1）时，最后一项变成 `+ a·(1/m − 1)`，需要多画。
- 最后还要加两项：羽化宽度 e（截断边从 alpha=0 过渡到实心的宽度，按 t0 屏幕像素算），和安全余量 s。【通用工艺】s 取 o 的 25%，且不少于 16 px。
- 所以底板在每一侧至少要画到画框外 **o + e + s**。
- 适用范围：这个公式假设层面正对相机、转角较小。遇到滚转、扩张中心不对称、大角度摇镜时，要改用逐帧投影四个角的数值方法（附录 B 的 shotA_check.mjs 就是这样做的）。仓库里**没有**现成的出血或露边检查工具（未实现）。

**算例：镜头 A**（【仓库实证·复算】Tx = 4.000、Ty = 0.076、Tz = 46.016，没有转角，f = 3700）

| 层 | D | f·Tx/D | m | 扩张抵扣 960·(1 − 1/m) | 需要的左右出血 o | 整段实有的最小出血 |
|---|---|---|---|---|---|---|
| sky | 20000 | 0.7 | 1.0023 | 2.2 | ≤ 0，只需安全余量 | 215 px |
| river | 1450 | 10.2 | 1.0328 | 30.5 | ≤ 0 | 240 px |
| mist | 1300 | 11.4 | 1.0367 | 34.0 | ≤ 0 | 390 px |
| bund（左边） | 520 | 28.5 | 1.0971 | 84.9 | ≤ 0 | 400 px |
| mist2 | 480 | 30.8 | 1.1060 | 92.0 | ≤ 0 | 340 px |

结论：在镜头 A 里，推镜扩张的速度比横移暴露边缘的速度快，所以按公式其实不需要出血；仓库实际留了 200–400 px，给日后改机位留足了余量。复算还确认，不透明的 sky 和 river 两层在 72 帧里每帧都盖满画面（17×10 网格采样，0 个空洞）。

**反算：如果把镜头 A 改成同样幅度的拉镜**（Tz = −46 m）：

- river：m = 0.969，o = 10.2 + 960·(1/m − 1) = 10.2 + 30.5 = **40.7 px**。
- bund 底边：扩张中心在 y = 520 + f·tan1.4° = 610，所以 a = 430；o = 430·0.0885 + 0.5 ≈ **38.5 px**，实有 113 px。
- bund 左边：o = 28.5 + 85 = **113.4 px**，实有 400 px。

也就是说，镜头 A 即使改成拉镜也不会露边。但如果要加一个 3° 的摇镜，平面底板需要 f·tan3° ≈ **194 px** 的出血，天空现有的 215 px 余量几乎会被用完。几度以上的摇镜应该改用穹顶。

**算例：镜头 C 的穹顶**（用角度来算）。

- 水平方向需要覆盖：从（最小摇角 − 半水平视场 − 余量）到（最大摇角 + 半水平视场 + 余量）。
- 【仓库实证·复算】镜头 C 的水平角 ψ ∈ [−3.0°, 17.7°]，水平视场 54.2°，所以至少要覆盖 [−30.1°, 44.8°]。sky_tall 穹顶覆盖 [−55°, 63°]，两侧各余 24.9° 和 18.2°。
- 竖直方向：仰角 θ ∈ [9.96°, 31.42°]，竖直视场 31°，所以至少要覆盖 [−5.5°, 46.9°]。天空穹顶覆盖 [−3°, 76°]；最下面那 2.5° 由 river 穹顶 [−16°, 0.25°] 和 mist 穹顶 [−2.2°, 8.5°] 接住。
- 逐帧检查：120 帧，每帧 25×14 个方向采样，没有一个方向落在 sky 或 river 之外。

**羽化宽度要实测。**【仓库实证·复算】alpha 从边界处的 0 升到 ≥200 所需的宽度：

- clouds_front_a 左边：1% 处为 42，2% 处为 133，3% 处为 222，5% 处达到 255。也就是图宽的 3–5%，在镜头 A 里约 45–75 屏幕像素。
- clouds_back 两端：约 5%，而且 8% 以内的平均 alpha 仍然很低。
- skyline_bund 右端、skyline_pudong 两端：约 3%。

**硬规矩：截断边（原图被画幅切断的那条边）在整段运动中都必须留在画外。** 羽化只能救"刚好擦边"的情况，救不了"整条边进画"（plates.json 的提示见 :176, :206, :314；验收要求见 docs/routes/validation-and-rtx.md:320）。仓库里有两个反例，详见 §5 第 1 行。

### 2.2 分辨率与输出

**放大系数 K 与纹素密度。**【仓库实证】K = 输出高 / 设计高（engine/stage/film.js:20-21）。设计高是 1040（src/main.js:20）。原生 4K 是 3840×2080，所以 K = 2（package.json:12；build.sh:13）。镜头在设计尺寸里摆位，渲染器、后期和显示层用实际像素（film.js:2-4）。

纹素密度的定义：

```
ρ = 贴图像素宽 / (屏幕设计像素宽 × K × 整段最大放大 m)
所需贴图宽 ≥ wpx × K × m_max × ρ_目标
```

【通用工艺】最终输出、最大放大时，ρ ≥ 1。绘画质感的底板，ρ 在 1–2 之间最合适；ρ 远大于 2 时，多出来的像素会被 mip 降采样掉，画面上看不到，只是白占显存。

**镜头 A：起始帧 1080 与结尾帧 4K 的纹素密度。**【仓库实证·复算】

| 层 | 1080 起始帧 ρ | 4K 结尾帧 ρ | 4K 下 1:1 需要的宽 | 现有宽 |
|---|---|---|---|---|
| sky（sky_dawn） | 1.51 | **0.75** | 4711 | 3548 |
| cloudsBack | 2.12 | 1.05 | 4130 | 4344 |
| cloudsFront（clouds_front_a） | 2.05 | 1.00 | 3061 | 3072 |
| pudong | 2.22 | 1.08 | 3300 | 3548 |
| river | 1.48 | **0.72** | 4956 | 3548 |
| bund | 2.90 | 1.32 | 3288 | 4344 |
| corner（clouds_front_b） | 3.09 | 1.38 | 2580 | 3548 |
| mist、mist2、veil（重复平铺） | 4.39 / 5.57 / 7.62 | 2.12 / 2.52 / 3.74 | — | 3512 |

**镜头 C 的穹顶按"每度多少像素"来算。**屏幕中心处每度的像素数：1080 下是 1875·π/180 = 32.7，4K 下是 65.4。【仓库实证·复算】各穹顶的 ρ：

| 穹顶 | 1080 | 4K |
|---|---|---|
| sky_tall 横向 | 0.92 | 0.46 |
| sky_tall 竖向 | 1.32 | 0.66 |
| clouds_back | 1.05 | 0.53 |
| skyline_pudong | 3.61 | 1.81 |
| river | 0.83 | 0.42 |
| mist（重复 2.2 次） | 1.57 | 0.79 |

如果要在 4K 下中心 1:1，sky_tall 横向需要 118°×65.4 ≈ 7722 px（现有 3548），clouds_back 需要 126°×65.4 ≈ 8243 px（现有 4344）。

**"×2 放大"不增加细节。**【仓库实证】所有彩色底板都是原图放大一倍得来的（plates.json:4, 9）。这样做能避免 1:1 显示时插值发虚，但细节的上限仍然是原图的分辨率。

【仓库实证·渲染】t=7.5 的 4K 静帧，与 1080 静帧放大 2 倍对照同一块区域：云形边缘的清晰度差不多，但 4K 的纸纹更细。仓库对 4K 的结论是"原生 4K 最好"（docs/渲染与4K.md:9），比较的是墨线、纸纹和显示层文字（docs/渲染与4K.md:62-66），**并不能说明底板在 4K 下够清楚**。如果要出 4K，A 镜头的 sky_dawn、river 和 C 镜头的各个穹顶都要按上表重新出图或放大。【通用工艺】柔和的天空在 ρ 为 0.5–0.75 时常常还能接受，云边和天际线剪影最好保持 ρ ≥ 1。

**显存。**【仓库实证】13 张底板全部常驻约占 0.45 GB（含 mipmap），plates.json 建议按镜头加载（plates.json:11）。但 main.js 是一次性加载 11 张（src/main.js:26-27）。分辨率翻倍，显存就变成 4 倍。按镜头加载【未实现】。

**纸纹尺度。** 外部纸纹按输出像素 1:1 平铺、不随 K 缩放，4K 下纸纹颗粒相对画面小一半（【仓库实证】`engine/look/compose.js:33-36`；`engine/look/paper.js:68-72`；`src/look.js:45`）。原因、观感取舍和修法（`paper.scale = K`）统一放在 [video.md §3.3](video.md)。

### 2.3 Alpha 与边缘

**仓库的约定。**【仓库实证】底板用直通 alpha（非预乘），透明区的 RGB 已经填上颜色、向外扩散，防止 mipmap 出黑边（plates.json:4, 7）。×2 放大是在预乘空间里做的（plates.json:4）——【通用工艺】这是正确的重采样方法，可以避免透明色渗进边缘。

**实测确认。**【仓库实证·复算】逐像素统计 7 张透明底板：

- alpha=0 的像素 **100%** 带有非黑的 RGB（均值是淡紫或淡粉，例如 clouds_back 为 (197, 152, 183)）。
- 可见像素里，有 9.7%–44% 的像素 RGB > alpha。这在预乘图里不可能出现，证明它们确实是直通 alpha。
- 各图的 alpha 包围盒和 plates.json 登记的"内容框"相差不到 0.005（例如 clouds_back 实测 [0.007, 0.09, 0.993, 0.848]，登记 [0.008, 0.09, 0.991, 0.847]）。

**A 路线全程直通。**【仓库实证】three 的贴图缺省 `premultiplyAlpha=false`（node_modules/three/src/textures/Texture.js:61），材质缺省 `premultipliedAlpha=false`（node_modules/three/src/materials/Material.js:83），cutoutPlane 的彩色层也显式写了 false（plates.js:80）。

**B 路线不要预乘。**【仓库实证】原生端的图片卡在生成 mip 链时，会在线性空间里把直通 alpha 预乘一次，所以**输入不能预先预乘**（docs/routes/raea-native.md:279）。

**四方连续的边是不透明的。**【仓库实证·复算】mist_low 左右两列的 alpha 是 255，这样横向平铺才无缝：首末两列的平均差 1.74，中间相邻列的平均差 0.38（8 位色阶）。代价是：用它做一条**在画内结束**的条带时，端头是一道硬切口。见 §5 第 1 行的 veil。

【通用工艺】边缘检查流程：

- 把底板分别放在纯黑底和纯白底上看。
- 透明区 RGB 没填，在低层 mip 会出黑边或白边。
- 重复预乘，边缘会比内部更暗。
- 在 sRGB 和线性空间里预乘不一致，软边上会出现细暗线。
- 颜色外扩至少要覆盖实际会用到的 mip 层级。例如 ρ≈4 的雾带会取到第 2 层 mip，外扩就要超过 alpha 边 4–8 px。仓库的做法是把透明区全部填满，任何 mip 层级都够用。

### 2.4 色彩空间

**分类设置。** 彩色底板和画布贴图标 sRGB，纸纹等数据贴图标 NoColorSpace（【仓库实证】`engine/stage/plates.js:21`、`engine/stage/plates.js:50`；`engine/look/paper.js:47`）。`src/main.js:27` 传的 `linear:['paper']` 不生效但无害。完整规则和错标后果见 [threejs.md §2.3](threejs.md)。

**底板颜色会被调色改变。**【仓库实证】处理链是：主场景渲到线性 HalfFloat → 雾 → bloom → 调色 → OutputPass 转 sRGB → Kuwahara（在 sRGB 空间做）→ 合成（index.js:3-6, 121-138）。渲染器输出 sRGB、不做色调映射（film.js:25），底板也不做色调映射（plates.js:30）。但底板**仍然要经过调色**（暖度、提亮、饱和度，见 src/shotA.js:150），所以成片里的颜色不等于 PNG 里的颜色。验色时用 `?dbg=scene` 看线性原图，再看成片。

**文件本身。**【仓库实证·复算】底板都是 8 位 RGB/RGBA，没有内嵌 ICC 配置（sips 和 ffprobe 均显示无色彩标签），所以一律按 sRGB 处理。【通用工艺】生成工具导出的 Display P3 图或带配置的图，交付前要转成 sRGB 并去掉配置。大面积的平滑渐变（天空）在 8 位下，经过提亮和 gamma 调整后可能出现色带；本片的颗粒（0.65，src/shotA.js:151）和纸纹能起到抖动作用。如果仍有色带，可以交 16 位 PNG，但 16 位贴图这条路**未在仓库里验证**。

**纸纹的实测与文档出入。**【仓库实证·复算】纸纹均值 0.50、标准差 0.11，与登记一致（plates.json:396），四方连续无缝（首末列差 6.43，相邻列差 6.47）。文档与实现有一处出入：plates.json:396 推荐"soft-light，强度 0.25–0.35"，而实际合成用的是乘法调制 `c *= 1 + 强度·2·(纸 − 中性点)`（compose.js:33-36），强度只有 0.12–0.14（src/look.js:45；src/shotA.js:151；src/shotB.js:63；src/shotC.js:209）。

**色板。**【仓库实证】plates.json 登记了共享色板：天顶、薰衣草、粉、杏橙地平线、云影、云亮边、城市剪影、窗灯（plates.json:14-23）。所有底板在后处理时都向这套色板做过色彩对齐（plates.json:4）。

### 2.6 不要把文字烘焙进底板

【仓库实证】眼镜显示层、片名这类文字，是在后期之后单独画到顶层二维画布上的（engine/stage/film.js:2, 30-33, 46-47；docs/作品.md:43-51），从来不进底板。原因有三：

- 进了底板，文字会被 Kuwahara、纸纹、颗粒处理，还会跟着产生视差；
- 4K 下要重新光栅化文字；
- 文案可能要改。

底板登记里描述城市时，只写剪影和窗灯（plates.json:218, 287）。

【通用工艺】AI 生成的底板常带伪文字（招牌、水印、签名），要画掉；不出现品牌标识；楼宇招牌保持抽象。

## 3 镜头语法

### 3.1 导演定调

【仓库实证】docs/作品.md:67-72 规定：

- 默认用固定机位或缓推；不变焦、不甩镜、不斜构图。
- 城市段用长焦压缩，构图竖向压迫；海面段用广角，构图横向舒展。
- 不做长时间的正面特写。
- 节奏由慢到更慢，再突然爆发。

各对象的帧节拍不同：镜头、云、水每帧都动；人物一拍二；鲲被困时一拍三（docs/作品.md:76-84）。

### 3.2 焦段

【仓库实证·复算】下表的等效焦距按"全画幅 24 mm 画面高"换算，换算本身属于【通用工艺】。

| 镜头 | 竖直视场 | 水平视场 | 等效焦距 | 出处 |
|---|---|---|---|---|
| A 雾江（城市） | 16° | 29.1° | ≈85 mm | src/shotA.js:19 |
| B 她 | 30° | 52.6° | ≈45 mm | src/shotB.js:13 |
| C 鲲现（仰望） | 31° | 54.2° | ≈43 mm | src/shotC.js:23 |
| B 路线例片三段 | 40° / 34° / 42° | 67.8° / 58.9° / 70.6° | ≈33 / 39 / 31 mm | examples/raea/film.tsx:68-70 |

"城市段长焦"落在镜头 A。"海面段广角"在 10 秒样片里**没有对应镜头**（未实现）。

**在这套引擎里，"压缩"到底由什么决定？** 因为 placeOnScreen 把 t0 的画面固定住了：

- 视场只决定"每米相机运动换算成多少像素"，即 f 的大小；
- **各层之间的视差比例只由 D 的比例决定**。

所以要"长焦压缩"：选窄视场，并让想压在一起的那几层 D 的比例很小（镜头 A 的城市一带是 1300、1450、1500）。要"广角舒展"：选宽视场，并放进 D 很小的近景层，拉开深度比，比如前景只有几十米、远景有上千米。

### 3.3 推、拉、摇、移、升降在 2.5D 里各起什么作用

| 运镜 | 视差 | 对底板的要求 | 仓库实例 | 适合 |
|---|---|---|---|---|
| 推（相机前移） | 有，近层放大更多 | 出血最省；分辨率要按结尾的放大倍数算 | 镜头 A 推 46 m：外滩放大 1.097 倍，天空 1.002 倍（src/shotA.js:20, 91-93） | 引向主体、积累情绪；全片的默认手段（docs/作品.md:69） |
| 拉（相机后退） | 有，各层收缩 | 出血最费，要多画 a·(1/m − 1) | 仓库的镜头都没用 | 揭示环境、收尾 |
| 变焦 | 无，所有层等比缩放 | 只需要分辨率 | 作品.md:69 明确不用；镜头 B 改用二维分层系数来模拟推镜（src/shotB.js:34） | 压平画面、制造窥视感 |
| 摇、仰（纯旋转） | 无 | 平面底板会变形并露边，改用穹顶；覆盖范围按 §2.1 的角度算法 | 镜头 C 上摇、左摇，片尾下摇（src/shotC.js:26-41, 155-157）。【复算】水平角 −3.0°→17.7°，仰角 23°→31.4°→10.0° | 跟随视线、揭示天空 |
| 移（横移） | 最强 | 侧向出血 f·T/D | 镜头 A 左移 4 m（src/shotA.js:93） | 展示层次 |
| 升降 | 竖向视差 | 竖向出血；地平线在画面上的位置只由俯仰决定，不随升降移动 | 镜头 A 在世界里上升 1.2 m，但换算到相机系竖向只有 0.076 m（复算）：推镜方向是世界水平方向，而相机仰了 1.4°，正好抵消了上升 | 改变俯视关系 |
| 跟拍 | 取决于目标 | 同摇镜 | 镜头 C 有 trackAim，但跟拍系数 `tk` 缺省为 0（src/shotC.js:136-154），也就是默认不跟 | — |
| 微晃 | 极小 | 留 1° 以内的余量 | 镜头 C 头部微晃小于 1°、频率低，不做手持抖动（src/shotC.js:35-38） | 第一人称 |
| 环绕／弧移 | 最强，而且面片的朝向会被看穿 | 面片永远朝着起始机位，环绕时被斜看，角度约为 atan(相机横移／D)；【通用工艺·建议】超过约 2°–3° 就改用穹顶或真实几何，或让近层只负责遮挡、不承担主体（需看片） | 仓库的镜头都没用。【推断·复算】若在镜头 A 绕渡船（约 928 m）环绕 5°，相机横移约 81 m：外滩层（D=520）被斜看约 8.9°，城市层（约 1500）约 3.1°，天空（20000）约 0.2°——近层会读成纸板 | 揭示空间关系；慎用 |

**速度上限。**【仓库实证·复算】镜头 C 片尾下摇的峰值是 24.4°/s（t≈9.21），在 1920×1040 下相当于每帧 33.3 px，是全片最快的运动；中段左摇峰值 9.5°/s。【通用工艺】24 fps、180° 快门的实拍经验是：高反差的硬边沿运动方向穿过画面至少要 5–7 秒，否则容易抖（judder）；写成与分辨率无关的比例，就是每秒移动不超过画面（横移按画宽、竖移按画高）的约 1/5–1/7。A 路线没有运动模糊，同样的速度频闪更明显，应取更严的一端。柔软的云对速度更宽容。按此对照镜头 C 的 9.0–9.5 秒：峰值时约 1.3 秒扫过一个画高，比经验值快约 4–5 倍（按画宽算也有 2–3 倍），而且硬边天际线在画内——列为看片重点【推断，需看片】。北冥定调本身要求"不甩镜"（`docs/作品.md:69`）。

**运动模糊。** A 路线没有（engine、src、lab 中都搜不到相关实现）【未实现】。C 路线有三种现成写法，都是对相机运动做子帧累积，只作方法参照（三件都是 historical-render）：`cases/source/keynote-B-kaitou/main.js:583-590` 平移时按屏幕速度取 4–20 个子采样平均；`cases/source/style-52-hologram-hud/film.js:432-440` 只在甩镜内做 5 个子帧、180° 快门，显示层只画一次以保持锐利；`cases/source/style-77-desktop-flythrough/src/main.js:39-50` 按相机角速度自适应快门，子帧累积加 Halton 抖动，把拖影限制在约 8 px。后两段代码来自风格库甲的示例（见本章出处段），借用时保留其许可声明。【通用工艺】三渲二的取舍：只对相机运动做子帧累积；一拍 n 的角色在快门内姿态不变；显示层和字幕不参与累积。成本是 N 倍渲染。C 路线还有一个例子用画布模糊给快速层做拖影，见 §7。

### 3.4 缓动怎么选

【仓库实证】缓动函数都在 engine/core/math.js:9-17, 33-55。下表中"峰值/平均"指峰值速度与平均速度之比；数值是解析计算的结果。

| 缓动 | 峰值/平均 | 起止特性 | 仓库用法 | 适合 |
|---|---|---|---|---|
| 近线性 `u·(1.18 − 0.18u)` | 1.18 | 一开始就有速度，结尾略收 | 镜头 A 的推镜（src/shotA.js:92）：片头就在走，切出时仍在动 | 跨越剪辑点的持续运动（【通用工艺】在运动中切） |
| `ss`（smoothstep） | 1.5 | 起止速度为 0，加速度不为 0 | 云墙消散（src/shotC.js:68），鲲浮出云海（src/shotA.js:106） | 物件位移、淡入淡出 |
| `ss5`（五次 smootherstep） | 1.875 | 起止的速度和加速度都为 0（math.js:16-17："镜头推拉用它更柔"） | 镜头 C 的上摇和片尾下摇（src/shotC.js:31, 156） | 镜头在本镜头内起步和停稳 |
| `eo`（三次缓出） | 3.0（在起点） | 起得猛，落得软 | 云墙拉开（src/shotC.js:67） | 揭示、拉开 |
| `ei` / `eio` | 3.0 | 加速收尾 / 两头缓 | 显示层动画（src/hud.js:94, 142） | 镜头上慎用，作品.md:69 不许甩镜 |
| `monotone`（单调三次样条） | 由关键帧决定 | 关键帧之间不过冲（math.js:33-34） | 目前只用在造型上（engine/form/loft.js:22），镜头没用 | 多关键帧的镜头曲线 |

缓动与视差的关系：观众是从各层**速度的差别**读出深度的。缓动改变的是速度随时间的变化，各层之间的速度比例不变（由 D 决定）。所以起步和停稳要柔（用 ss5），中段最好有一段速度稳定的区间，让视差能被看清。

### 3.5 分层帧节拍

【仓库实证】engine/core/clock.js:2-3 规定：镜头和雾每秒 24 帧平滑运动，角色一拍二，大型生物一拍三。src/shotA.js:95-108 是具体例子。镜头 C 的跟拍瞄准点用的是连续、没有量化的姿态，而鲲本身一拍三（src/shotC.js:136）。

三维主体的轨迹是确定性的：按"航向 × 速度"逐帧积分（engine/stage/motion.js:16-23），镜头 C 鲲的支点轨迹就是这样得到的（src/shotC.js:102）。所以任意一帧都可以单独重渲，三维物体与底板之间的视差也能逐帧复现，分段并行渲染时不会在切点上错位。

【通用工艺】2.5D 的铁律：**相机和底板的运动默认不量化。** 如果相机按一拍二步进，所有层会一起跳，观众读到的就是"一张静止图在二维里平移"，纵深感就没了。副作用与例外：相机跟拍一拍 n 的主体时，主体会在画框里按拍跳动、相对画框发抖。二选一处理——主体的根运动走平滑、只让姿态按拍（渡船的做法，src/shotA.js:113-117）；或相机瞄准连续轨迹（镜头 C 的 `trackAim` 用连续、未量化的姿态求瞄准点，src/shotC.js:136-145）。只有整幅画面就是一张画、不需要表达纵深时，才考虑相机与主体同拍步进。 各对象节拍的完整规则见 [animation.md §2](animation.md)。

## 4 避免"纸板感"

### 4.1 三维物体与底板的交互

纸板感的成因【通用工艺】：

- 同一层内部视差完全一样；
- 剪影边缘发硬，又没有空气感；
- 三维物体和底板之间没有遮挡、没有接触；
- 光向对不上；
- 层太少；
- 视差给得太强，暴露出"它是一张平片"。

仓库里的对策：

| 交互 | 仓库做法 | 证据 |
|---|---|---|
| 遮挡：前后夹 | 鲲夹在前后两层云之间，城市剪影挡在鲲前面 | src/shotA.js:2-4, 27-32, 58-66；【渲染】t=2.95 |
| 遮挡：穿插 | 云片按距离分两档 order（小于 200 m 用 5.5，否则用 3），在鲲前后穿过；软边是椭圆遮罩 | src/shotC.js:115-127, 176-182；plates.js:54-75 |
| 雾：盖住接缝 | 低雾条带盖住"江面上沿 / 天际线水岸线"这条接缝；鲲腹下加一条薄雾，让它像泡在云海里 | src/shotA.js:30-35, 40-46 |
| 雾：三维进雾 | FogExp2 的雾色取底板色板（§1.4） | src/shotA.js:18；src/shotC.js:22 |
| 光包裹 | 2D 画布层已有 `lightWrap`：用整层 alpha 做遮罩，沿外沿渗入渐变色，人物层在用；三维与底板之间靠加色辉光叠在云堤和低雾之上（"光从云后透出来"）和后期 bloom 近似；人物逆光边的光带模糊后垫在剪影底下 | engine/paint/light.js:10, 52；src/girl.js:592；src/shotC.js:54-58, 185-186；engine/look/index.js:124；src/girl.js:595-598 |

### 4.2 视差强度的分寸

【仓库实证·复算】镜头 A 三秒之内各层的运动量：

| 层 | 运动量 |
|---|---|
| 天空 | 0.7 px |
| 城市 | 约 10–11 px |
| 外滩 | 横移 28 px，加放大 9.6% |
| 角上近云 | 157 px（主要来自放大） |

远与近的横移视差之比约为 1:50。这是样片的取值（样片只有间接认可痕迹）；新镜头以看片为准，不把它当成通则。

**竖直卡片当地面用，会出问题。** 镜头 A 的江面是一张深度固定为 1450 m 的竖直卡片（src/shotA.js:36），但画面底部那片水的真实距离只有约 500–900 m。

- 【复算】三秒内，外滩根部（D=520）相对江面卡片会滑移约 30–38 px（三个采样点的位移矢量长度）；渡船所在的深度（928 m）相对江面会滑移约 9–11 px。
- 仓库用近雾 mist2 盖住外滩根部，渡船自己也在运动，所以这两处滑移都看不出来。
- 规则：一层如果横跨很大的深度范围（地面、水面），就要拆成不同 D 的几条，或者改用真正的水平面。plates.json:348 也写了"作地面时可在着色器里按 y 做透视压缩"——这一点【未实现】。B 路线的江面就是一张真正的三维水平面（examples/raea/film.tsx:86）。
- 【通用工艺】另一种通行做法是**投影贴图**（camera projection）：把画好的底板从起始机位投到简单的代理几何上（地面平面、楼体的长方体），相机移动时透视自然正确。three 里的做法是自定义着色器按 t0 相机的投影矩阵算 UV【未实现】。适用条件：相机位移远小于到代理几何的距离；代理的背面没有画面内容，转过去就露馅。

**尺度与深度的关系。**【仓库实证·复算】天际线底板里，上海中心画在屏幕上约 576 px 高。如果按 D=1500 m 去理解，它对应的实际高度只有 233 m（真实高度约 632 m）；按真实高度反推，这张画的比例相当于 4.06 km 外。也就是说，这一层的视差按 1.5 km 给，画的大小却是 4 km 外的样子。好在相机只横移 4 m，两种距离算出的视差只差约 6 px，看不出来。【通用工艺】一旦三维物体要在楼群之间穿插（比如鲲从两栋楼之间游过），就必须按物理尺度重新摆 D，否则遮挡关系和大小会互相矛盾。鲲约 590–600 m 长（src/shotC.js:214 的标记点：吻部 x=300，尾部 x=−290；docs/作品.md:30）。

### 4.3 屏幕空间纸纹的淋浴门效应

【仓库实证】纸纹按屏幕像素固定（compose.js:34 用的是 `gl_FragCoord`），颗粒每帧换种子（compose.js:42-47）。相机运动时，所有层都在一张不动的纸"下面"滑过。【通用工艺】这就是非真实感渲染文献里说的淋浴门效应（shower-door effect）：屏幕空间的纹理不随物体运动。慢推、慢摇时接近手绘动画的观感，可以接受；快摇时这层纸会被看出来。北冥的定调本来就以缓推为主，所以影响不大。如果以后要做快速运动镜头，修法的关键词是把纹理锚定在物体或世界空间、动态纸纹（dynamic canvas）——【未实现】。

### 4.4 景深

【通用工艺】景深是 2.5D 卖纵深的主要手段之一：焦内锐、焦外虚，引导视线；焦点转移（拉焦）能在不动机位的情况下换主体。在三渲二里，景深和 Kuwahara 的远近半径都按深度变化，作用相近但不同：Kuwahara 改的是笔触尺度，景深改的是清晰度；两者同时用，焦外会既虚又粗，要先决定由谁负责"远"。

【仓库实证】A 路线没有景深实现（engine、src、lab 中都搜不到）【未实现】。现有替代：镜头 B 的天空底板预先虚化（src/shotB.js:2："轻微虚焦当景深"）；按深度加大笔触半径（§1.6）。焦点转移【未实现】；C 路线 `style-41-paper-popup` 的相机关键帧带光圈和焦点两项（cases/source/style-41-paper-popup/TREATMENT.md:29），写法可以参照。

## 6 迁到 B 北冥原生路线 · BNE 时的差异

【仓库实证】例片的结构（examples/raea/film.tsx）：

- 最底下是二维页面层的天空 `<img>`，每秒左漂 2 px（:74）；
- 上面是 `Canvas3D layered`（:75）；
- 世界空间里放了四张 ImagePlane：云堤 z=−140，天际线 z=−100，左、右前景云 z=−25 和 −31，全部 `shadow={false}`（:84-93）；
- 一张真正的三维水平江面 `ShaderMesh Plane3d`（:86）；
- 三维的鲲和船；
- 一道近岸栏杆，用来提供可测量的前景视差（:98-100）；
- 关闭了距离雾（:81）。

迁移要点：

1. **不要照搬 A 路线的 placeOnScreen 思路**。原生端用世界坐标和宽度来摆卡片（docs/routes/raea-native.md:29：宽度是场景单位，高度默认随图片比例）。所以应先在 A 路线里确定每层的屏幕矩形和 D，再换算成世界坐标和宽度，并核对宽高比（§5 第 4 行）。
2. **天空要能跟随相机旋转**。把天空放在页面层只能解决露边，解决不了旋转视差（§5 第 5 行）。原生端用天空球或穹顶是否可行，要在目标版本上实测，本章没有验证。
3. **alpha**：输入直通 alpha、透明区填色；不要预乘（raea-native.md:279）。
4. **采样**：ImagePlane 没有公开采样器（raea-native.md:282），没法像 A 路线那样设各向异性，所以更要避免非等比缩放和 ρ < 1。
5. **雾**：例片关掉了距离雾。要恢复空气透视，只能在画面上表达，或者等预乘、雾、遮罩的处理顺序验证之后再开（docs/raea/experiment.md:31）。
6. **笔触按深度变化**：A 路线靠 cutoutPlane 的深度遮罩加 Kuwahara；原生端没有对等实现。"原版墨线和 Kuwahara 与此实现视觉等价"属于未验证项（docs/raea/experiment.md:40；docs/raea/integration.md:154, 162）。
7. **验收**：前后层要有真实视差；近机位、远机位都不能露出图片的矩形边；字幕要在目标层级上（docs/routes/raea-native.md:41）。底板与 alpha 一项，要在"最大相机运动处"检查（docs/routes/validation-and-rtx.md:320）。

## 附录 B 复现命令与核算脚本

渲染命令都在仓库根目录执行，输出写到仓库以外的目录：

```sh
node engine/render/still.mjs . 0 1.5 2.95 4 5.2 6.4 7.5 9.9 --size 1920x1040 --query nohud=1 --out <输出目录> --prefix final_
node engine/render/still.mjs . 0 2.95 --size 1920x1040 --query "nohud=1&dbg=scene" --out <输出目录> --prefix scene_   # 线性原图，最容易看出露边
node engine/render/still.mjs . 0 7.5 --size 3840x2080 --query nohud=1 --out <输出目录> --prefix k4_                  # 4K 对照
```

核算脚本没有入库，放在本次会话的草稿区 `<研究工作区>/tools/`。本章引用的静帧和裁切对照图在 `<研究工作区>/stills/`：`crop_scene0_edge_zoom.jpg` 是镜头 A 的露边，`cmp_75_clouds.jpg` 和 `cmp_0_river.jpg` 是 1080 与 4K 的对照，`crop_bne_cloudedge.jpg` 和 `crop_bne_skyline.jpg` 是 B 例片联系图的放大。这些脚本只读仓库，并按绝对路径导入 `engine/stage/camera.js` 和 `node_modules/three`：

- `shotA_check.mjs`：镜头 A 每层的视差、放大倍数、边缘进画情况、纹素密度、滑移量，以及不透明层的覆盖。
- `shotC_check.mjs`：镜头 C 的摇镜范围、角速度、穹顶覆盖与边缘、辉光方位、塔尖投影位置。
- `bne_check.mjs`：B 例片的截断边和机位朝向（基于 §5 写明的假设，属于【推断】）。
- `misc_check.mjs`：地平线、雾量、等效焦距、穹顶纹素密度。
- `alphastats.mjs`、`edgeprofile.mjs`、`seam.mjs`：底板的 alpha 统计、羽化曲线、接缝与纸纹统计。用法是 `ffmpeg -v error -i assets/plates/<名>.png -f rawvideo -pix_fmt rgba - | node <脚本> …`。

建议把 `shotA_check.mjs` 的逐帧投影方法做成仓库工具，用来检查底板露边和纹素密度——【未实现】。
