# 北冥导演与画面规范

> **解决什么**：让进入仓库的 agent 拿到一个需求后，知道按什么顺序导、画风怎么定、在本仓库里怎么做到、做成什么样算过、哪些能力还没有——无论走 A 北冥风格路线 · WebGL 三渲二、B 北冥原生路线 · BNE，还是从 C 北冥代码动画风格 · 86 式 取方法。
> **状态**：定稿（入库前版本），基线 `origin/main 3b97946`。"仓库实证"都附了 `文件:行号` 或可在仓库根重跑的命令；没实现的能力标【未实现】；行业通行做法标【通用工艺】，不声称仓库已实现。文件里的仓库路径一律相对仓库根；规范内部互链用相对路径。
> **方法来源**：导演十步的骨架和多数判定条目改编自第三方风格库甲的导演手册（MIT）；本仓库作品用来补证据、补数字、提供反例。C 路线的 66 部风格样片本身就是按该方法做的。逐条出处见 [SOURCES.md](SOURCES.md)。

## 四条硬口径

1. **状态三分离**：已输出、技术检查通过、用户认可分开记录。`cases/catalog.json` 的 historical-render 只表示出过片；rejected 的三件只当反例，不作任何正面依据（`docs/TRACKS.md:57`；`AGENTS.md:58`）。
2. **看片分两层，不能互相代替**：agent 做"代理审片"（帧条、切点邻帧、逐帧变化曲线、声画对齐图、读字与安全区检查），结论只能写"代理检查通过"；全速带声的完整观看由用户或指定审片人做，记下审片人、日期和原话，agent 不替人勾选（`AGENTS.md:38`"技术检查通过不能替代观看整片"；`docs/routes/validation-and-rtx.md:324` 第 8 节"全片与声音"一行）。做法见 DIRECTING 步骤 10。
3. **不把设计稿报告成已有能力**：本规范的 style-lock、作品工程描述、动态预演开关、各种检查脚本都是【未实现】的设计；阐述模板的示例也只许用已有能力，需新写的写明"需新写"。
4. **借来的要标出处**：C 路线历史作品的技法和部分代码来自风格库甲的示例；借用前查 [SOURCES.md §3](SOURCES.md)，沿用代码时保留原版权与许可声明（`THIRD-PARTY.md:36`）。

```sh
python3 tools/check_directing_docs.py --self-test
python3 tools/check_directing_docs.py <规范目录>
```
